# 请求旅程：一个 `/chat` 请求要过几道关

> **面试时照着这个讲。** 每道关都写清：什么情况触发、返回什么、代码在哪。

---

## 全景

```
POST /chat
  │
  ├─① 鉴权 ─────────── 401             auth.py
  ├─② 限流 ─────────── 429 + Retry-After  ratelimit.py
  ├─③ 请求体校验 ───── 422             schemas.py
  ├─④ 选后端 ───────── 400             fastapi_bot.py
  ├─⑤ token 裁剪 ───── 不拒绝，只处理    tokens.py
  ├─⑥ 调模型（重试） ─ 502             fastapi_bot.py
  ├─⑦ 降级 ─────────── 换下一个后端      fastapi_bot.py
  └─⑧ 流式返回 ─────── 200 + 四个响应头
```

## 三种性质（这一段最能区分懂不懂）

| 阶段 | 性质 | 为什么这么分 |
|---|---|---|
| ①–④ | **拒绝** | 请求本身不合格，挡在门外，不浪费一分钱 |
| ⑤ | **处理** | 请求合法但太长，想办法让它能走完，而不是拒绝 |
| ⑥–⑦ | **兜底** | 请求没问题，是我的上游出问题了，换路走 |
| ⑧ | **如实报告** | 成功就说是谁服务的，失败就说清是谁的错 |

> 把「校验」和「超时」都叫成"检验"就丢了这个区分——**一个是拒绝，一个是处理，一个是兜底。**

## 逐关

### ① 鉴权 —— `auth.py` · `require_api_key`

| | |
|---|---|
| 触发 | 没带 `X-API-Key`，或值不对 |
| 返回 | `401 {"detail":"无效的 API Key"}` |
| 设计点 | **fail closed**：服务端没配 `GATEWAY_API_KEY` 时拒绝所有请求，而不是默认放行 |
| 设计点 | **常数时间比较**：用 `secrets.compare_digest` 而不是 `==`，防时序侧信道 |
| 踩过的坑 | Header 带中文时 `compare_digest` 抛 `TypeError` → 曾返回 500。改成按 bytes 比较 |

### ② 限流 —— `ratelimit.py` · `rate_limit`

| | |
|---|---|
| 触发 | 同一个 key 在 60 秒滑动窗口内超过 20 次 |
| 返回 | `429` + `Retry-After: 37` |
| 设计点 | **滑动窗口**，不是"每分钟重置"——固定窗口在边界前后各打满一次就能突破限额 |
| 设计点 | 只挂 `/chat`，因为只有它花钱 |
| 已知限制 | 计数在内存里，多 worker 会放大 N 倍（要 Redis） |

### ③ 请求体校验 —— `schemas.py` · `ChatRequest`

| | |
|---|---|
| 触发 | 字段缺失/类型错/越界：`history_len ≤ 10`、`query` 长度、`role` 只能是 system/user/assistant |
| 返回 | `422` + **拍平过的字段列表** `[{"field","reason"}]` |
| 设计点 | `extra="forbid"`：多传字段直接拒绝，不静默忽略 |
| 设计点 | `content` 归一化：Gradio 6 会传内容块数组，这里统一转成字符串（否则第二轮必 422） |

### ④ 选后端 —— `fastapi_bot.py` · `chat()`

| | |
|---|---|
| 触发 | `payload.provider` 指了一个不存在的名字 |
| 返回 | `400 {"detail":"未知的 provider：'xxx'；可用的有：[...]"}` |
| 设计点 | **显式指定就不降级**——用户说"我要 ollama"，服务端不该偷偷换成别的 |

### ⑤ token 裁剪 —— `tokens.py` · `trim_history`

| | |
|---|---|
| 触发 | 历史 + system + 本轮 query 超过窗口的 70% |
| 返回 | **不拒绝**。从最旧的历史开始丢，响应头写 `X-History-Trimmed: 13` |
| 设计点 | system prompt 和本轮 query **永远保留**（语义地基） |
| 设计点 | 估算用 `cl100k_base`，对中文**高估约 60%**——宁可多裁，不能超窗口 |
| 踩过的坑 | 按"条"丢，不按"字"砍；所以最后可能空出几百 token 用不上 |

### ⑥ 调模型 + 重试 —— `fastapi_bot.py` · `_open_stream`

| | |
|---|---|
| 触发 | 超时（connect 5s / read 15s）、429、5xx、连不上 |
| 重试 | 同一后端最多 3 次，指数退避 1s/2s |
| 不重试 | 400/401/403/404/422——同一把错 key、同一个错请求，试一百次都一样 |
| 设计点 | **首 token 前置**：先拿到第一个 chunk 才返回 `StreamingResponse`，否则状态行已经发出去了，改不了 |

### ⑦ 降级 —— `fastapi_bot.py` · `_open_stream_with_fallback`

| | |
|---|---|
| 触发 | 这个后端重试耗尽仍失败，或者 key 错（401） |
| 动作 | 按降级链换下一个后端 |
| 链的顺序 | `default` → `priority` 里点名的 → 其余探测通过的（按 toml 段顺序）→ 探测失败的 |
| 总预算 | `LLM_FALLBACK_BUDGET=50s`，超了就不再往下试（否则最差延迟翻倍） |
| 设计点 | 探测失败的后端**不踢掉**，只标"未验证"——网络抖动会误判 |
| 已知限制 | 慢超时（连上不响应）时预算会被第一个后端吃光，**基本不会降级**——这是故意的，慢死的后端值得等 |

### ⑧ 返回 —— `fastapi_bot.py` · `generate_response`

| | |
|---|---|
| 成功 | `200` + 四个响应头 |
| 全失败 | `502 {"detail":"上游模型服务不可用：..."}` |
| **上游 4xx** | **透传 4xx + 上游原话**，不包成 502 |

四个响应头：

```
X-Provider       : 实际服务的是谁（可能是降级后的）
X-Model          : 实际用的模型
X-Fallback-From  : 从哪个后端降下来的（没降级就没有这个头）
X-History-Trimmed: 丢了几条历史（没裁就没有这个头）
```

> **为什么需要 `X-Provider`**：实测中三个模型分别自称"通义千问""OpenAI 的 ChatGPT""AI 助手"——**模型的自述不可信，只有响应头说了实话。**

## 所有错误码一张表

| 状态码 | 谁的问题 | 触发 | 该不该重试 |
|---|---|---|---|
| `401` | 你 | key 没带 / 不对 | 不该 |
| `422` | 你 | 请求体字段不对 | 不该 |
| `400` | 你 | 未知 provider / 上游说请求太长 | 不该 |
| `429` | 你 | 超频 | 等 `Retry-After` |
| `502` | 我 | 上游超时 / 5xx / 连不上 | 可以 |
| `500` | 我 | 服务端缺配置（比如没配 key） | 不该 |

## 面试怎么讲（30 秒版）

> 「一个请求进来要过 8 道关。
>
> 前 4 道是**拒绝**：鉴权 401、限流 429、请求体校验 422、未知后端 400——不合格的请求挡在门外，不浪费一分钱。
>
> 第 5 道不是拒绝是**处理**：token 超预算就裁掉最老的历史，让超长对话还能继续。
>
> 第 6、7 道是**兜底**：同一个后端重试 3 次，彻底不行就换降级链上的下一个，总预算 50 秒封顶。
>
> 最后一道是**如实报告**：成功就带 `X-Provider` 告诉你谁服务的；全挂了就 502；但如果是上游说"你的请求有问题"，我透传 400 而不是包成 502——因为那是你的错，重试没用。」

## 这张图怎么用

| 场景 | 怎么用 |
|---|---|
| 复习 | 从全景图往下，每次只看一关的"触发/返回/代码在哪" |
| 面试 | 直接背「30 秒版」，被追问哪一关就翻到那一节 |
| 加新功能 | 先想清楚它插在哪一关、属于"拒绝/处理/兜底"哪一种 |
| 排查 bug | 从 401 到 502 顺着排——**先确认请求走到了哪一关** |
