# PR #2 计划：让服务扛得住上游故障

> 状态：**计划中**，尚未开工。
> 前置：PR #1 已合并（master `b24d4c1`）。
> 目标：把"上游一挂，用户只收到半句话"这个最危险的失败模式修掉。

---

## 一、一句话目标

> 上游模型服务超时 / 报错 / 半路断流时，客户端应该**明确收到一个错误**，而不是拿到 `200 OK` 加半句话。

---

## 二、为什么是这三件事

PR #1 补的是"进来的请求合不合法"（校验 + 鉴权）。
但服务的另一半风险在**出口**：我们会去调别人的服务，而别人的服务会挂。

现状的三个洞：

| 洞 | 现在的行为 | 用户感受 |
|---|---|---|
| 没有超时 | 上游不响应就一直等 | 页面转圈，几十秒后浏览器自己断 |
| 没有重试 | 一次网络抖动就整轮失败 | "怎么又失败了"，再点一次可能就好 |
| 流式开始后报错 | `StreamingResponse` 已经把 200 发出去，异常被吞在生成器里 | 回复说到一半停住，**而且看起来像正常结束** |

第三个最严重：它**不报错**。监控看不到、日志没有、用户以为模型就这么答的。

---

## 三、范围

### 做

1. **超时**：连接超时 + 读取超时分开设，可配置
2. **重试**：只对可重试的错误重试，指数退避，次数可配置
3. **首 token 前置校验**：先拿到第一个 chunk 再返回 `StreamingResponse`，
   把"开始即失败"这类错误变成明确的 `502`
4. **测试**：3 条，覆盖上面三个行为
5. **故障演练**：手动制造故障，录下来

### 不做（留到 PR #3）

- 多供应商降级（需要第二个可用端点）
- 限流（和韧性是两件事）
- SSE 协议标准化 + 中途断流的错误帧（改动大，单独一个 PR）
- 结构化日志 / metrics / token 计量

> **范围控制的原则**：一个 PR 只讲一个故事。这次的故事是"我让失败变得可见"。

## 五、每个任务的实现提示（不是答案，是方向）

### T1 复现故障

```powershell
# 备份 .env 里那一行，改成不存在的域名
# SILICONFLOW_BASE_URL=https://example.invalid/v1
python fastapi_bot.py
```

然后用 `tools/smoke_auth.py` 里那条正常请求打一次，**掐表**，把结果记下来。

> 重点不是"看到报错"，是**记录它现在是怎样失败**。没有这一步，后面所有改动你都证明不了"变好了"。

### T2 超时

现在是 `ChatOpenAI(api_key=..., base_url=..., model=...)`。
`ChatOpenAI` 支持传 `timeout`，但**建议你显式传，并且在 `get_model()` 里从环境变量读**：

```
LLM_CONNECT_TIMEOUT=5
LLM_READ_TIMEOUT=60
```

思考题：为什么 `connect` 和 `read` 要分开设？
（提示：握手失败和"连上了但不吐字"是完全不同的故障，前者应该很快放弃。）

### T3 重试

不要引入 `tenacity`，用最朴素的循环：

```
for attempt in range(1, MAX_ATTEMPTS + 1):
    try:
        ...
        return
    except <可重试的异常> as e:
        if attempt == MAX_ATTEMPTS: raise
        await asyncio.sleep(2 ** attempt)   # 2s, 4s, 8s
```

**关键判断：哪些异常该重试？**

| 情况 | 重试？ | 理由 |
|---|---|---|
| 连接超时 / 读取超时 | ✅ | 网络抖动，重试有意义 |
| 429 限流 | ✅ | 等一下再来 |
| 5xx | ✅ | 对方临时故障 |
| 400 参数错误 | ❌ | 重试一百次也一样错 |
| 401 key 无效 | ❌ | 你的问题，不是网络的 |
| 422 | ❌ | 同上 |

> 这条表是面试高频考点：**"无脑重试"是新手最典型的错误**，它会把一个参数错误放大成三次无效请求，还会加重对方限流。

### T4 首 token 前置（本次最核心的改动）

现在是这样：

```python
async def generate_response():
    async for chunk in bound.astream(messages):   # ← 异常在这里面
        ...
return StreamingResponse(generate_response(), ...)   # ← 200 已经发出去了
```

改成"先拿第一个，再决定要不要返回流"：

```
stream = bound.astream(messages)
try:
    first = await anext(stream)
except Exception:
    raise HTTPException(502, "上游模型服务不可用")   # ← 这时还没发响应，能返回真正的错误码

async def generate_response():
    yield first.content
    async for chunk in stream:
        ...
```

思考题：
- 为什么这样能返回 502？（提示：`StreamingResponse` 一旦开始 yield，状态行就已经发出去了）
- 这样做之后，**还没解决**的是什么？（提示：第 2 个 token 之后断流，依然会静默结束）

### T5 测试

FakeModel 要能"假装失败"。给它加个参数，比如让 `astream` 直接 `raise`：

| 测试 | 断言 |
|---|---|
| 上游超时 → 返回 502 | `status_code == 502`，且响应体里有人话 |
| 400 类错误 → **不重试** | 调用计数 == 1（证明没有无脑重试） |
| 正常请求 → 仍然是流式 200 | `r.text == "你好"`，内容和以前一致 |

> 第三条是**回归保护**：你改了返回路径，必须证明正常路径没被改坏。

### T6 演练

录 30 秒：把 `SILICONFLOW_BASE_URL` 改成坏地址 → 请求 → 看到 502 → 改回来 → 请求 → 正常出字。

这段视频比 README 里十行字都有说服力。

## 七、面试怎么讲（提前想好）

> 我的服务要调上游大模型。最初没有超时也没有重试，最糟的一个问题是：
> `StreamingResponse` 一旦开始输出，HTTP 状态行就已经发出去了，
> 所以上游中途报错时，客户端收到的是 `200 OK` 加半句话——
> **它看起来像正常结束**，监控和日志都发现不了。
>
> 我的做法是：先把第一个 chunk 取出来，拿到之后再构造响应。
> 这样"开始就失败"的情况会变成明确的 502，而不是伪装成成功。
> 重试只针对超时、429 和 5xx，400/401 这类参数错误绝不重试——
> 无脑重试会把一个错误放大成三次无效请求。

**这个故事的价值**：它证明你想的不是"功能跑通"，而是"失败时会发生什么"。
