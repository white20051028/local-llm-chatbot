## 二、三个比知识点更重要的认知

### 1. 「失败要可见」比「功能能跑」更难，也更值钱

功能跑通只是及格线。真正让人踩坑的是——**失败被伪装成成功**。
`200 OK` + 半句话，监控看不到、日志没有、用户以为模型就这么答的。

> 以后写任何对外接口，都问自己一句：**它失败时，客户端能知道吗？**

### 2. 重试的判据不是「出错了」，是「再试一次有可能成功」

| 情况 | 重试？ | 想清楚为什么 |
|---|---|---|
| 连不上 / 超时 | ✅ | 网络抖动，第二次可能就好了 |
| 429 限流 | ✅ | 等一会儿再来 |
| 5xx | ✅ | 对方临时故障 |
| 400 参数错 | ❌ | 你的请求本身有问题，试一百次一样 |
| 401 key 错 | ❌ | 同上，而且会加重对方限流 |

**无脑重试是新手最典型的错误**：它把 1 个错误放大成 3 个无效请求。

### 3. 「改了没生效」永远是第一个怀疑对象

今天踩了 **4 种**不同形态：

| 形态 | 判断方法 |
|---|---|
| 模块缓存（改了 `.py` 没重启） | 进程启动时间 vs 文件修改时间 |
| `.env` 不热重载 | `--reload` 只管 `.py`，配置要手动重启 |
| `$env:X` 优先级高于 `.env` | `Remove-Item Env:X` 或开新终端 |
| `--reload` 没加 | 看启动命令里有没有这个参数 |

> 出问题时先问「它现在到底用的是哪份配置」，而不是先看代码。
> `/health` 回显 `base_url` / `timeout` 就是为这个加的。

## 三、12 道自测题

分三档。**答不上来不丢人，答不上来说明该看哪里**——每题后面标了去哪找答案。

### 能解释（概念层）

1. 为什么 `StreamingResponse` 一旦开始 yield，就不能再改状态码了？
   → `fastapi_bot.py` 里 `_open_stream` 上方的注释
   答：因为一旦开始yield就已经对判断码做出过判断并分类了，如果不先提前检测yield的第一个内容，很有可能发生用户没拿到结果但是后端显示200 ok的情况
2. `APITimeoutError` 为什么能被 `APIConnectionError` 的 `isinstance` 捕获？
   → `_is_retryable()` 的注释
   答：因为APITimeoutError 是 APIConnectionError 的子类，超时报错是连接不上报错的其中一部分
3. 400 和 500 的重试策略为什么不同？
   → 本文第二节
   答：因为400的错误是由于用户自己输入的参数问题报的错，不改参数怎么重试都没用。而500报错可能是系统自身问题，可以先重试尝试恢复
4. 为什么每次重试都要重新 `bound.astream(messages)`，而不是复用上一个流？
   → `_open_stream()` 里那句"每次重试都要新建一个流"
   答：因为重试是由于后端取上一个流的第一个有内容的chunk检验发现挂掉了，才会开始重试的，如果不新建一个流的话重试就没有意义了，那只要第一次挂掉就一定会重试挂满。重试时新建流才有重试后真的连上去了的可能
5. 为什么必须在 `return StreamingResponse` **之前**把第一个 chunk 取出来？
   → 
   答：因为一旦开始yield就已经对判断码做出过判断并分类了，如果不先提前检测yield的第一个内容，很有可能发生用户没拿到结果但是后端显示200 ok的情况

### 能预测（理解层）

6. 把 `LLM_MAX_ATTEMPTS` 改成 `1`，用假上游测，耗时和日志条数变成什么？
答：耗时变为15.02秒左右，日志条数只有一条，ERROR:    调用上游失败
7. 把 `LLM_READ_TIMEOUT` 改成 `3`，最差耗时大概是多少？算一算，别猜。
答：最差耗时大概是3*15+数据传递时间4秒=49秒左右
8. 如果上游返回的是 **500**（不是超时），会重试几次、日志几条、最终状态码是什么？
答：如果返回的是500，会重试LLM_MAX_ATTEMPTS次，日志LLM_MAX_ATTEMPTS-1条warning和一条是失败，最终状态码是502
9. 如果代码里删掉 `max_retries=0`，那个 48 秒会变成多少秒？为什么？
答：如果删掉，48秒会变成3*48=144秒，因为隐式重试默认重试3次，每次都会自动多次请求
10. 如果断流发生在**第二个** chunk 之后（已经吐出一个字了），客户端会收到什么？为什么这个还没修？
答：200，ok  没修可能是为了给后续的更优化的技术铺垫
### 能改（迁移层）

11. 如果要加「总时间预算 30 秒」（到点就不再重试），你会改哪个函数？大概怎么改？
答：_open_stream函数，给函数加一个时间规则，如果从调用函数开始过了大概30秒还没有通过的话就暂停重试，直接返回超时
12. 如果有人说"重试让用户等 48 秒太蠢了，删掉重试"，你会怎么折中？
答：我会给项目前端页面加一个可修改的参数来让用户自己决定要不要开启重试。默认开启，觉得太慢的用户只需要点一下按钮就可以自行关闭

## 四、三个「先预测、再验证」的实验

**这是消化的核心动作。** 不要读完就过——先在纸上写下预测，再跑，再看差异。

### 实验 A（10 分钟）：把重试次数改成 1

```powershell

# 终端 A：python tools/silent_upstream.py
# 终端 B：$env:SILICONFLOW_BASE_URL="http://127.0.0.1:8899/v1"
#         python -m uvicorn fastapi_bot:app --port 6066 --reload
# 终端 C：python tools/probe_failure.py
```

先写预测：耗时约 __16__ 秒，WARNING 约 __1__ 条。
跑完填：实际耗时 __0.5__ 秒，WARNING __1__ 条。
目标: http://127.0.0.1:6066/chat
  HTTP 状态 : 502  ← 客户端拿到了明确错误
  耗时      : 0.46 秒
  响应内容  : '{"detail":"上游模型服务不可用：OpenAIConnectionError"}'
(llm-dev) PS D:\桌面\多轮对话机器人项目>
**差异在哪，为什么？**

### 实验 B（10 分钟）：把读超时改成 3 秒

`LLM_READ_TIMEOUT=3`，重跑实验 A。
先算：3 次 × 3 秒 + 退避(1+2) = 多少？实测对不对？

### 实验 C（10 分钟）：把"不可重试"换成"可重试"

打开 `tests/test_api.py`，把 `test_400错误不重试` 里的 `openai.BadRequestError` 换成 `openai.InternalServerError`。
先预测 `boom.calls` 会变成几，再跑测试。

> 这一条能一次验证两件事：你对"可重试"的理解，以及测试是不是真的在保护行为。

## 附：批改记录（2026-10-23）

**总评**：12 题里扎实 5 题（2/3/4/8/11）、需修正 6 题（1/5/7/9/10/12）、无效实验 1 个。

### 需要修正的答案

| 题 | 你的说法 | 修正 |
|---|---|---|
| 1 / 5 | "yield 之后对状态码做过判断分类" | 没有"判断分类"。是 HTTP 协议：状态行 + 头 + 正文按顺序单向写入 socket，**开始写正文后状态行早发出去了，网络没有撤回操作** |
| 7 | 3×15+4 = 49 秒 | 题目是 `LLM_READ_TIMEOUT=3`：3 次 × 3 秒 + 退避(1+2) = **约 12 秒**。公式：`次数 × 读超时 + 退避总和` |
| 9 | "默认重试 3 次"，48×3=144 | `max_retries=2` = **重试 2 次 / 共 3 次尝试**。正确：外层 3 × 内层 3 = 9 次 × 15s = **135 秒** + 退避 ≈ 140 秒。144 是碰巧接近 |
| 10 | "没修可能是为了后续技术铺垫" | 错。原因有二：① HTTP 无法反悔（同第 1 题）；② **纯 text/plain 流里没有"错误帧"**，要修必须换 SSE（`text/event-stream` 的 `event: error`）。⚠️ 不知道就说不知道，别编合理理由 |
| 12 | "让用户选要不要重试" | 反模式：用户不懂什么叫重试。更好的折中：降读超时(15→10，最差 33s) / 只重试 1 次(最差 20s) / 按错误类型给不同次数 / 加总预算 30s |

### 实验 A 无效，必须重做

| | 数值 |
|---|---|
| 预测 | 16 秒 |
| 实测 | 0.46 秒 |
| 报错类型 | `OpenAIConnectionError`（**不是** `Timeout`） |

0.46 秒 = 连接被瞬间拒绝 → 那次请求**根本没连上假上游**（`silent_upstream.py` 没启动，或残留 `example.invalid`）。
所以它验证的不是"重试次数"，而是"连不上能多快失败"。

**重做前置检查**：启动假上游后必须看到
`fake upstream listening on 127.0.0.1:8899`，再启动服务。
