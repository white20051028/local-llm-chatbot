## 二、三个核心认知

### 1. 「失败要可见」比「功能能跑」更难，也更值钱

`200 OK` + 半句话，监控看不到、日志没有、用户以为模型就这么答的。

> 以后写任何对外接口，都问一句：**它失败时，客户端能知道吗？**

### 2. 重试的判据不是「出错了」，是「再试一次有可能成功」

| 情况 | 重试？ | 为什么 |
|---|---|---|
| 连不上 / 超时 | ✅ | 网络抖动，第二次可能就好 |
| 429 限流 | ✅ | 等一会儿再来 |
| 5xx | ✅ | 对方临时故障 |
| 400 参数错 | ❌ | 请求本身有问题，试一百次一样 |
| 401 key 错 | ❌ | 同上，还会加重对方限流 |

### 3. 「改了没生效」永远是第一个怀疑对象

| 形态 | 判断方法 |
|---|---|
| 模块缓存（改了 `.py` 没重启） | 进程启动时间 vs 文件修改时间 |
| `.env` 不热重载 | `--reload` 只管 `.py`，配置要手动重启 |
| `$env:X` 优先级高于 `.env` | `Remove-Item Env:X` 或开新终端 |
| `--reload` 没加 | 看启动命令 |

## 三、错题本：12 道自测题

### 第 1 题：为什么 `StreamingResponse` 一旦开始 yield 就不能改状态码？

❌ **我写的**
> 因为一旦开始yield就已经对判断码做出过判断并分类了，如果不先提前检测yield的第一个内容，很有可能发生用户没拿到结果但是后端显示200 ok的情况

✅ **正确答案**

**没有"判断分类"这回事。** 原因是 HTTP 协议本身：

```
HTTP 响应 = 状态行("HTTP/1.1 200 OK") + 响应头 + 响应体   ← 按顺序单向写入 socket
```

一旦开始往 socket 写**响应体**，状态行早就发出去了。**网络上没有"撤回"操作**——无法追回已发出的字节说"刚才那个 200 是假的"。

🔍 **我错在哪**
我描述的是**后果**（用户没拿到结果但显示 200），不是**原因**（协议层单向流 + 响应头已发送）。
"判断码做出过判断并分类"这句是自己编的机制，实际不存在。

> 补一句：`StreamingResponse` 的设计就是"边算边发"，所以状态码必须在返回之前确定——而那一刻异常还没发生。

### 第 3 题：400 和 500 的重试策略为什么不同？

❌ **我写的**
> 因为400的错误是由于用户自己输入的参数问题报的错，不改参数怎么重试都没用。而500报错可能是系统自身问题，可以先重试尝试恢复

✅ **答对了** ✅（"系统自身问题"更准确的说法是"对方服务器的临时故障"）

🔍 **这题对在哪**
抓住了重试的本质判据：**再试一次有没有可能不同**。
400 的输入不变 → 结果必然相同；500 是对方偶发 → 有可能恢复。

### 第 4 题：为什么每次重试都要重新 `bound.astream(messages)`？

❌ **我写的**
> 因为重试是由于后端取上一个流的第一个有内容的chunk检验发现挂掉了，才会开始重试的，如果不新建一个流的话重试就没有意义了，那只要第一次挂掉就一定会重试挂满。重试时新建流才有重试后真的连上去了的可能

✅ **基本正确** ✅（表述绕，但抓住了"旧流已废，必须新建"）

更精确的说法：异步生成器**抛出异常后就终止了**。再迭代旧流不会重新发请求，只会立刻抛 `StopAsyncIteration`。
所以重试 = **重新发起一次完整请求**，必须新建。

🔍 **可以改进的地方**
"只要第一次挂掉就一定会重试挂满"这个推理对，但没点出"为什么"——因为旧流是**一次性**的，异常后不可复用。

### 第 9 题：删掉 `max_retries=0` 后，48 秒会变成多少？

❌ **我写的**
> 如果删掉，48秒会变成3*48=144秒，因为隐式重试默认重试3次，每次都会自动多次请求

✅ **正确答案**

`max_retries=2` 的意思是 **「重试 2 次」= 总共 3 次尝试**（1 次原始 + 2 次重试），**不是"重试 3 次"**。

两层相乘：

```
外层 3 次尝试 × 内层 3 次尝试 = 9 次 × 15 秒 = 135 秒  + 退避 ≈ 140 秒
```

🔍 **我错在哪（这是最危险的一种错）**
**结论碰巧接近（144 ≈ 140），但推理是错的。**
把"每一层都变 3 倍"当成了"整体变 3 倍"（48 × 3），而正确算法是两层相乘。
数字撞对了，下次换个参数（比如 `max_retries=1`）就会错得离谱。

> **「对的答案 + 错的推理」比错的答案更危险**，因为它不会暴露问题。

### 第 10 题：断流发生在第 2 个 chunk 之后，客户端收到什么？为什么没修？

❌ **我写的**
> 200，ok  没修可能是为了给后续的更优化的技术铺垫

✅ **正确答案**

客户端收到 **`200 OK` + 已经发出的那部分内容**，然后连接结束——**看起来像正常说完了**。

没修的原因是两条，都指向同一个地方：

1. **HTTP 无法反悔**（同第 1 题）：200 和部分正文已经发出
2. **纯 `text/plain` 流里没有"错误帧"这种表达方式**：正文就是正文，中间插不进"我出错了"

要修必须**换协议**——SSE（`text/event-stream`），才能发一条独立的 `event: error`。这是 PR #3 的工作量。

🔍 **我错在哪**
**不知道，然后编了一个听起来合理的理由。**
"为了后续技术铺垫"——这句如果被面试官追问"那你说说怎么铺垫的"，就穿了。

> 改成：**「我不知道，我猜是 X，需要验证。」** 这样永远安全。

### 第 11 题：加「总时间预算 30 秒」，改哪个函数、怎么改？

❌ **我写的**
> _open_stream函数，给函数加一个时间规则，如果从调用函数开始过了大概30秒还没有通过的话就暂停重试，直接返回超时

✅ **答对了** ✅

实现要点：

```python
import time

deadline = time.monotonic() + 30          # ← 用 monotonic，不用 time.time()
for attempt in ...:
    ...
    remaining = deadline - time.monotonic()
    if remaining <= backoff:              # 剩下的时间不够睡一轮了，就别再试
        break
    await asyncio.sleep(backoff)
```

🔍 **可以补的一点**
用 `time.monotonic()` 而不是 `time.time()`——后者会被系统时钟调整影响（NTP 校时、手动改时间），可能算出负数或超长。

### 第 12 题：有人说"重试让用户等 48 秒太蠢，删掉重试"，怎么折中？

❌ **我写的**
> 我会给项目前端页面加一个可修改的参数来让用户自己决定要不要开启重试。默认开启，觉得太慢的用户只需要点一下按钮就可以自行关闭

✅ **为什么这个方向偏了**

**把工程决策推给用户是反模式。** 用户不知道什么叫"重试"，他只知道"这网站卡了"。
而且这个开关会变成"出了问题没人知道该开还是该关"。

更好的折中（按代价从低到高）：

| 方案 | 最差耗时 | 代价 |
|---|---|---|
| 读超时 15 → 10 | ~33 秒 | 改一行配置 |
| 只重试 1 次（2 次尝试） | ~20 秒 | 改一个默认值 |
| 按错误类型给不同次数 | ~20–35 秒 | 稍复杂 |
| 总预算 30 秒封顶 | 30 秒 | 第 11 题已经想到 |

🔍 **我错在哪**
出发点是好的（在意用户体验），但**解法是"加一个开关"，而不是"改进默认行为"**。
好的工程是：默认设置就该是合理的，而不是让用户自己去调。

## 四、三个实验（含失败的那次）

### 实验 A 第一次：**实验无效**

| 项 | 数值 |
|---|---|
| 我的预测 | 16 秒 |
| 实测 | **0.46 秒** |
| 报错类型 | `OpenAIConnectionError`（**不是** `Timeout`） |
| 假上游日志 | 只有 `listening`，**没有** `accepted a connection` |

**为什么无效**：`silent_upstream.py` 被 Ctrl+C 关掉了（日志里 `KeyboardInterrupt` at `s.accept()`）。
服务去连一个已经关闭的端口 → 瞬间失败。
**它验证的不是"重试次数"，而是"连不上能多快失败"。**

### 实验 A / B 的正确结果（用 `tools/measure_retry.py`，一条命令）

| 配置 | 连接次数 | 总耗时 | 理论值 |
|---|---|---|---|
| `read_timeout=15, attempts=1` | 1 | **15.09 秒** | 15.0 秒 |
| `read_timeout=3, attempts=3` | 3 | **12.14 秒** | 12.0 秒 |
| `read_timeout=2, attempts=3` | 3 | 9.13 秒 | 9.0 秒 |

**判断工具是否真在工作，只看一件事**：假上游有没有打印 `accepted a connection`。

### 实验 C：第一次"失败"，但失败得很有价值

第一次改：把 `BadRequestError` 换成 `InternalServerError`，**但 `httpx.Response(400, ...)` 没改**。

结果：测试**通过**（`calls == 1`）。

**为什么**：`_is_retryable` 判断的是 `exc.status_code`，不是类名。`APIStatusError.status_code` 是从 `response.status_code` 读的——还是 400，所以判"不可重试"。

第二次改：状态码也改成 500 → 测试**失败**（`assert 3 == 1`）。

| 状态码 | 类名 | calls | 结果 |
|---|---|---|---|
| 400 | BadRequestError | 1 | ✅ 通过（不重试） |
| 400 | InternalServerError | 1 | ✅ 通过（类名不影响） |
| **500** | InternalServerError | **3** | ❌ 红（证明 500 会重试） |

> **"叫什么"不重要，"是什么"才重要。** 异常类名只是包装，判据在 `status_code` 里。
