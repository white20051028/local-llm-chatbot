## 二、三个比知识点更重要的认知

### 1. 「失败要可见」比「功能能跑」更难，也更值钱

功能跑通只是及格线。真正让人踩坑的是——**失败被伪装成成功**。
`200 OK` + 半句话，监控看不到、日志没有、用户以为模型就这么答的。

> 以后写任何对外接口，都问自己一句：**它失败时，客户端能知道吗？**

### 2. 重试的判据不是「出错了」，是「再试一次有可能成功」

| 情况 | 重试？ | 想清楚为什么 |
|---|---|---|
| 连不上 / 超时 | ✅ | 网络抖动，第二次可能就好了 |
| 429 限流 | ✅ | 等一会儿再来 |
| 5xx | ✅ | 对方临时故障 |
| 400 参数错 | ❌ | 你的请求本身有问题，试一百次一样 |
| 401 key 错 | ❌ | 同上，而且会加重对方限流 |

**无脑重试是新手最典型的错误**：它把 1 个错误放大成 3 个无效请求。

### 3. 「改了没生效」永远是第一个怀疑对象

今天踩了 **4 种**不同形态：

| 形态 | 判断方法 |
|---|---|
| 模块缓存（改了 `.py` 没重启） | 进程启动时间 vs 文件修改时间 |
| `.env` 不热重载 | `--reload` 只管 `.py`，配置要手动重启 |
| `$env:X` 优先级高于 `.env` | `Remove-Item Env:X` 或开新终端 |
| `--reload` 没加 | 看启动命令里有没有这个参数 |

> 出问题时先问「它现在到底用的是哪份配置」，而不是先看代码。
> `/health` 回显 `base_url` / `timeout` 就是为这个加的。

## 四、三个「先预测、再验证」的实验

**这是消化的核心动作。** 不要读完就过——先在纸上写下预测，再跑，再看差异。

### 实验 A（10 分钟）：把重试次数改成 1

```powershell
# 改 .env：LLM_MAX_ATTEMPTS=1
# 终端 A：python tools/silent_upstream.py
# 终端 B：$env:SILICONFLOW_BASE_URL="http://127.0.0.1:8899/v1"
#         python -m uvicorn fastapi_bot:app --port 6066 --reload
# 终端 C：python tools/probe_failure.py
```

先写预测：耗时约 ____ 秒，WARNING 约 ____ 条。
跑完填：实际耗时 ____ 秒，WARNING ____ 条。
**差异在哪，为什么？**

### 实验 B（10 分钟）：把读超时改成 3 秒

`LLM_READ_TIMEOUT=3`，重跑实验 A。
先算：3 次 × 3 秒 + 退避(1+2) = 多少？实测对不对？

### 实验 C（10 分钟）：把"不可重试"换成"可重试"

打开 `tests/test_api.py`，把 `test_400错误不重试` 里的 `openai.BadRequestError` 换成 `openai.InternalServerError`。
先预测 `boom.calls` 会变成几，再跑测试。

> 这一条能一次验证两件事：你对"可重试"的理解，以及测试是不是真的在保护行为。
